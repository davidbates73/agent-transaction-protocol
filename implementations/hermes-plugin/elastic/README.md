# Hermes ATP → Elasticsearch + Kibana (reporting, slice 3)

Ships the Hermes ATP recorder's signed log (`~/.hermes/atp/records.jsonl`, see
[`../README.md`](../README.md)) into a single-node Elasticsearch on **us-solebay**, verifies
every record on the way in, and gives you two Kibana dashboards: an **overview** (sessions over
time, model calls and latency, tool calls by name, subagent links, verify failures) and a
**request lifecycle** view (one request's parent session and subagent sessions as a tree, every
model and tool step on a waterfall, the records in order, and rollups).

```
 nuc-hermes  (Hermes VLAN)                         us-solebay
 ┌───────────────────────────────┐  TCP 9200    ┌────────────────────────────────────┐
 │ Hermes + ATP recorder plugin  │  HTTPS only  │ es01  Elasticsearch (Basic, TLS)   │
 │   └─ records.jsonl (append)   │  one-way     │ kibana  127.0.0.1:5601 (not on the │
 │ hermes-atp-export (push)  ────┼──────────────┼─▶        Hermes VLAN)              │
 │   reads only; never blocks    │  OPNsense    │ setup   certs, roles, users,       │
 └───────────────────────────────┘  pass rule   │         template, dashboard        │
                                                └────────────────────────────────────┘
```

* **Push mode (default):** the exporter runs on nuc-hermes as a systemd service, follows the
  log and pushes to Elasticsearch on us-solebay over HTTPS on TCP 9200. That is the only flow
  the firewall needs to allow.
* **Copy mode (fallback):** you copy the log files to us-solebay yourself (rsync/scp) and the
  same exporter, run with `--once` from a timer, ships them locally. See [Copy mode](#copy-mode-fallback).
* Free **Basic** license only: built-in users, roles and TLS. There's no Logstash, ML, Watcher,
  alerting or SSO, and nothing that needs a trial.

| Path | What it is |
|---|---|
| `docker-compose.yml`, `.env.example` | ES + Kibana + one-shot `setup` service. Credentials come only from `.env` (gitignored). |
| `setup/setup.sh` | Idempotent setup: TLS certs, `kibana_system` password, roles, users, index template, dashboard import. |
| `setup/role-hermes-exporter.json` | Write-only exporter role: `create_doc` + `auto_configure` on `hermes-atp-records-*`, nothing else. |
| `setup/role-hermes-viewer.kibana.json` | Read-only viewer role: index `read` plus Kibana dashboard/discover/visualize `read`. |
| `setup/index-template.json` | Explicit mappings (`dynamic: false`; bodies stored but never indexed). |
| `kibana/hermes-atp-dashboard.ndjson` | Importable saved objects (data view, 7 Lens panels, dashboard), generated by `kibana/build_saved_objects.py`. |
| `kibana/hermes-atp-lifecycle.ndjson` | The request lifecycle dashboard (data view, 7 Lens tiles, 2 Vega panels, a saved Discover session, controls), generated by `kibana/build_lifecycle_dashboard.py`. |
| `exporter/hermes_atp_export.py` | The exporter: Python 3.9+ stdlib only. |
| `examples/` | systemd units (push service; copy service + timer) and exporter configs. |
| `tests/` | Fake-ES exporter tests and asset checks; `compose.hostnet.yml` is a test-only override. |

## What gets shipped

One Elasticsearch document per log line, in the monthly index `hermes-atp-records-YYYY.MM`.
The month comes from the record's own signed timestamp. Lines that can't be parsed go to
`hermes-atp-records-invalid`.

* **Fields:** these are explicit and allowlisted; anything the exporter doesn't know is
  dropped.
  * Identity: `@timestamp`, `session_id`, `root_session_id` (the whole request; see
    [root_session_id](#root_session_id-whole-request-grouping)), `parent_session_id`,
    `parent_turn_id`, `parent_subagent_id`, `turn_id`, `task_id`, `event`, `seq`,
    `is_session_start`.
  * Model and tool: `model`, `response_model`, `provider`, `tool_name`, `tool_call_id`,
    `api_request_id`, `status`, `status_code`, `error_type`, `finish_reason`,
    `duration_ms`, `api_duration_ms`, `tokens.{prompt,completion,total,…}`.
  * Hashes and lengths: input/output hashes and lengths.
  * Provenance: `node_id`, `parents`, `issuer_id`, `key_id`, `hermes_version`.
  * Source: `source.{path,offset,line}`.
  * Verify: `verify.{status,valid,authentic,errors}`, and `anomaly` (true exactly when the
    document got an `anomaly-*` `_id`, i.e. `verify.valid` is false).
* **Verification at ingest:** each line goes through the same checks as `atp_cli.py verify`,
  via the shared `atp_log.check_line` + `atp_log.chain_step`:
  * per-record checks: blank or invalid JSON, structure, nodeId, Ed25519 signature, body hash;
  * per-session chain checks: seq, previous-record link.

  `verify.status` is `valid` or the first error kind: `tampered`, `missing`, `out-of-order`
  or `body-mismatch`. This is **incremental and provisional**. The exporter sees each record
  once, in order, without the whole-log look-ahead, so a reordered record may show as
  `missing` where `verify` says `out-of-order`. Whole-log warnings (`unmatched-request`,
  `missing-parent-session`) aren't computed. The authoritative verdict is still
  `python3 implementations/python/atp_cli.py verify records.jsonl --pub key.pub`.
  For the record, the ingest result matched `verify` line for line on every log vector (see
  the tests).
* **Bodies are never shipped by default.** `body.input` / `body.output` are sent only when
  the record contains bodies (recorder `HERMES_ATP_LOG_BODIES=true`) **and** the exporter is
  started with `ship_bodies: true` / `--ship-bodies`. Even then they're stored but not
  indexed or searchable (`enabled: false`). The recorder already redacts secrets before
  hashing. The exporter adds nothing new: no headers, no environment, and nothing but the
  allowlisted fields.
* **Document `_id`:**
  * A record that passes every check is keyed by its **nodeId**: the content hash, signed by
    the recorder.
  * Anything else (tampered, forged signature, duplicate, out of order, unparseable) is keyed
    by `anomaly-` + sha256(sha256 of the file up to that line ‖ the line).

  Both are deterministic, so re-sending is always harmless. Documents are written with bulk
  `create`, and a 409 "already exists" counts as delivered. A forged copy of a record can't
  take the genuine record's `_id`, and a duplicated line shows up instead of being deduped
  away.

## Stand-up on us-solebay

Requirements:
* Docker Engine with the compose v2 plugin.
* About 3.5 GB of RAM to spare: ES heap 1 GB with a 2 GB container limit, Kibana 1.5 GB.
* `vm.max_map_count` of at least 262144.

```sh
# once, as root: Elasticsearch needs this (and it must survive reboots)
echo 'vm.max_map_count=262144' > /etc/sysctl.d/99-elasticsearch.conf && sysctl --system

# get this directory onto us-solebay, then:
cd implementations/hermes-plugin/elastic
cp .env.example .env && chmod 600 .env
$EDITOR .env      # every password/key (32+ random chars), ES_BIND_ADDR=<SOLEBAY_IP>,
                  # ES_PUBLIC_IP=<SOLEBAY_IP> (and/or ES_PUBLIC_HOSTNAME) for the certificate
docker compose up -d
docker compose logs -f setup      # ends with "[setup] setup complete"
```

The `setup` service:
1. Creates a self-signed CA and certificates in `./certs` (gitignored). The certificate SANs
   are `es01`, `localhost`, 127.0.0.1 and your `ES_PUBLIC_*` values.
2. Sets the `kibana_system` password.
3. Creates the **`hermes_exporter`** role and user (write-only), and the **`hermes_viewer`**
   role and user (read-only).
4. Installs the index template, and adds fields introduced later (`root_session_id`) to the
   mapping of indices that already exist.
5. Checks that the license is `basic`.
6. Imports both dashboards (overview, then request lifecycle).

It's idempotent: `docker compose run --rm setup` re-applies everything. After editing `.env`
it also re-sets the `hermes_exporter`/`hermes_viewer`/`kibana_system` passwords.

Check it from us-solebay. Each of these prompts for the `elastic` password, so the password
never lands in your shell history:

```sh
curl --cacert certs/ca/ca.crt -u elastic https://<SOLEBAY_IP>:9200/_license    # "type" : "basic"
curl --cacert certs/ca/ca.crt https://<SOLEBAY_IP>:9200                        # 401: no anonymous access
```

Notes:
* `ELASTIC_PASSWORD` only takes effect on the first start, when the data volume is empty. To
  change it later, run
  `curl --cacert certs/ca/ca.crt -u elastic -X POST https://<SOLEBAY_IP>:9200/_security/user/elastic/_password -H 'Content-Type: application/json' -d @-`
  and type `{"password":"…"}`, then update `.env`.
* **Certificates:** to issue new ones (for example after changing `ES_PUBLIC_*`), run
  `rm -r certs/es01 certs/kibana && docker compose run --rm setup && docker compose restart es01 kibana`,
  then copy the CA to the exporter again if you also replaced `certs/ca`.
* **Always up:** `es01` and `kibana` use `restart: unless-stopped` (the one-shot `setup` has
  none), so they come back after a reboot as long as Docker starts at boot:
  `sudo systemctl enable --now docker containerd`. A container you stopped by hand
  (`docker compose stop`/`down`) stays stopped across reboots until `docker compose up -d`.
  If they still don't come back, check `docker compose ps -a` and `docker compose logs es01`:
  a common cause is `ES_BIND_ADDR` (the LAN IP) not being up yet when Docker starts.
  Docker doesn't retry a failed port bind. Docker's unit already orders itself after
  `network-online.target`, but that target only waits if the host's wait-online service is
  enabled, so enable `systemd-networkd-wait-online` or `NetworkManager-wait-online`, whichever
  your host uses. If your Docker package's unit lacks those lines, add them with
  `sudo systemctl edit docker`, above the "Lines below this comment will be discarded" marker:

  ```ini
  [Unit]
  Wants=network-online.target
  After=network-online.target
  ```

  Or let the bind succeed before the address is up with `net.ipv4.ip_nonlocal_bind=1` in a file
  under `/etc/sysctl.d/` (`net.ipv6.ip_nonlocal_bind=1` if `ES_BIND_ADDR` is IPv6).
* **Data:** it lives in the `esdata` volume. `docker compose down` keeps it;
  `docker compose down -v` deletes it.
* **Retention:** there's no automatic retention. Indices are monthly, so delete old ones with
  `DELETE /hermes-atp-records-2026.01` (ILM is available on Basic; retention is the next backlog item).
* **Version:** `STACK_VERSION=9.5.6` in `.env` is the single pin for both images (compose
  requires it and has no fallback), so a bump is a one-line change. The saved objects
  carry Kibana 9.5 model versions; newer Kibana migrates them forward on import.

## Exporter

The exporter is stdlib Python 3.9+, run straight from this repo layout. It imports the
vendored `../atp.py` and `../atp_log.py`, which are byte-identical copies of
`implementations/python/`, so it's the same code as `verify`.

**Never blocks Hermes.** It opens the log `O_RDONLY` and never writes to it, locks it or
truncates it. It reads only complete lines (ending in `\n`) and never waits on the recorder.
If Elasticsearch is down, it stops reading and retries the same batch with capped exponential
backoff plus jitter (1 s → 60 s). The log itself is the buffer, so memory stays bounded and
nothing is lost.

**Checkpoint.** It keeps one checkpoint per log file in `state_dir`, written atomically
(tmp + fsync + rename) and only after Elasticsearch has acknowledged the batch. The checkpoint
holds the byte offset, the sha256 of everything shipped so far, and the per-session chain
state. On start, and whenever the file shrinks, the exporter re-hashes the already-shipped
prefix:
* If the file was truncated, replaced or rewritten, it starts over from byte 0. That's
  harmless because `_id`s are deterministic.
* Rotation (the path now names a new file) is handled by draining the old file to EOF and
  then following the new one, carrying session chain state across.
* Losing or corrupting the state directory only means re-sending, never duplicates. The
  session map (`sessions.json`, below) is relearned from the logs.

**Errors.**
* Per-item 429/5xx responses are retried.
* Any other per-item rejection is written to `state_dir/dead-letter.jsonl` with only the
  `_id`, offset, HTTP status and error type, never record content, and then skipped.
* Bad credentials, missing privileges or an untrusted certificate are fatal: exit code 3, so
  the journal shows them instead of a silent retry loop.
* A config error exits with code 1.

### root_session_id (whole-request grouping)

A Hermes request is a top-level session plus the subagent sessions it delegated to, and
theirs (nested). Only a subagent session's **first record** carries the link
(`parent_session_id`), so filtering on the parent's `session_id` alone misses its subagents.
The exporter therefore stamps every document that has a `session_id` with
**`root_session_id`**: the top-level session reached by following the links child → parent →
… . A top-level session's `root_session_id` is its own `session_id`. Filter on
`root_session_id : "<parent session>"` to get the whole request.

* **Export time only.** `records.jsonl`, its signatures and `atp_cli.py verify` are
  unchanged, and the document `_id` is still the record hash, so re-exporting stays
  idempotent with no duplicates.
* **Links are learned only from authentic records** (signature verified) and kept in
  `state_dir/sessions.json` (mode 0600, written atomically after each acknowledged batch, before
  the checkpoint). So roots survive restarts, multiple logs and copy-mode re-copies. Before
  each pass the exporter reads the links in every log's unread lines first, so a subagent is
  stamped with its full chain even when its parent's link is in another log listed later.
* **Out of order across runs.** If a link turns up only after some documents were shipped
  (for example the parent's log is copied in a later run), new documents get the right root
  at once, and the exporter logs a warning and lists the affected sessions under `restamp` in
  `sessions.json`. It can't fix the documents already shipped itself, on purpose: its role is
  `create_doc` only, so a compromised NUC can't rewrite history. Run
  `exporter/hermes_atp_restamp.py` on us-solebay (below), then
  `hermes_atp_export.py --config … --restamp-done` on the exporter host to clear the list.
* **Orphans.** A subagent session whose link was never recorded, or whose first record isn't
  in any exported log, can't be connected: it is its **own root**, like a top-level session,
  and shows as a separate request. A child whose parent's own link is missing stops at the
  parent (the parent is the root). If its link shows up later, the restamp above fixes it.
* **Cycles** (only possible with corrupt links) can't hang anything: every session on or
  leading into a cycle gets the smallest session id on the cycle as its root. If a session
  ever names two different parents, the smaller id wins. Both rules are independent of
  reading order, so the result is deterministic.
* **Lines that can't be parsed** have no session and get no `root_session_id`.
* **Size and pruning.** `sessions.json` holds a few short entries per session (roughly
  100–200 bytes each: its parent link, the root last stamped, when it was last seen). So
  that it doesn't grow forever, the exporter forgets sessions it hasn't seen a record of for
  `session_link_ttl_days` (default 30; `0` = never), checked at start and hourly. It never
  forgets a session still in use (seen within the TTL, or with records still waiting to be
  shipped) or listed for restamping, nor any session in the chain of ancestors of one of
  those, so their roots keep resolving. At 1,000 sessions
  a day the file stays around 3–6 MB. The one case pruning changes: a session that goes quiet
  for longer than the TTL and then records again (after its link was forgotten) is stamped as
  its own root from then on. Raise the TTL if Hermes sessions can pause that long. Rebuilding
  still works: delete `sessions.json` (or the whole `state_dir`) and every link is relearned
  from the logs.

**Backfill / restamp (existing indices).** The index template only applies to indices
created after it, and the exporter only creates documents. For indices written before
`root_session_id` existed:

```sh
# on us-solebay, from this directory (prompts for the elastic password; or set
# HERMES_ES_PASSWORD / --password-file)
python3 exporter/hermes_atp_restamp.py --es-url https://localhost:9200 --ca-cert certs/ca/ca.crt --dry-run
python3 exporter/hermes_atp_restamp.py --es-url https://localhost:9200 --ca-cert certs/ca/ca.crt
```

It (1) adds `root_session_id` to the mapping of every existing `hermes-atp-records-*` index
(`docker compose run --rm setup` does that too), (2) reads the links from Elasticsearch,
(3) works out the roots with the exporter's own code and (4) runs `_update_by_query` only for
documents whose `root_session_id` is missing or wrong. A second run changes nothing. By hand,
for one request whose sessions you know:

```sh
curl --cacert certs/ca/ca.crt -u elastic -X PUT "https://localhost:9200/hermes-atp-records-*/_mapping" \
  -H 'Content-Type: application/json' -d '{"properties":{"root_session_id":{"type":"keyword","ignore_above":1024}}}'
curl --cacert certs/ca/ca.crt -u elastic -X POST "https://localhost:9200/hermes-atp-records-*/_update_by_query?conflicts=proceed&refresh=true" \
  -H 'Content-Type: application/json' -d '{"query":{"terms":{"session_id":["<parent>","<child>","<grandchild>"]}},
  "script":{"source":"ctx._source.root_session_id = params.root","params":{"root":"<parent>"}}}'
```

Re-exporting with a cleared `state_dir` produces the same `_id`s, so it stamps
`root_session_id` only into **new** indices (for example after deleting the old ones, or with
a different `index_prefix`): into existing indices every `create` is a 409 and the old
documents stay as they were.

### Configuration

Settings are read from a JSON file (`--config`, or `HERMES_ATP_EXPORT_CONFIG`). Environment
variables override the file, and command-line flags override both. To see the resolved
settings with secrets masked, run `--check-config`.

| Key | Env | Default | |
|---|---|---|---|
| `mode` | `HERMES_ATP_EXPORT_MODE` | `push` | `push` follows the logs forever; `copy` (or `--once`) processes to EOF and exits |
| `es_url` | `HERMES_ES_URL` | required | `https://<SOLEBAY_IP>:9200` |
| `ca_cert` | `HERMES_ES_CA_CERT` | system CAs | Path to us-solebay's `certs/ca/ca.crt`. TLS verification can't be turned off. |
| `username` / `password_file` | `HERMES_ES_USERNAME` / `HERMES_ES_PASSWORD_FILE` | | `hermes_exporter` and a 0600 file holding its password (`password` / `HERMES_ES_PASSWORD` also work; prefer the file) |
| `api_key_file` | `HERMES_ES_API_KEY_FILE` | | Alternative to user/password: a file holding an encoded API key (`api_key` / `HERMES_ES_API_KEY` also work) |
| `logs` | `HERMES_ATP_EXPORT_LOGS` (`:`-separated) | `~/.hermes/atp/records.jsonl` | Log files to ship |
| `pub` | `HERMES_ATP_EXPORT_PUB` | required | The recorder's `key.pub`, used for verification |
| `state_dir` | `HERMES_ATP_EXPORT_STATE` | `~/.hermes/atp/export-state` | Checkpoints and dead-letter file (0700) |
| `ship_bodies` | `HERMES_ATP_EXPORT_SHIP_BODIES` | `false` | See "Bodies" above |
| `session_link_ttl_days` | `HERMES_ATP_EXPORT_SESSION_LINK_TTL_DAYS` | `30` | How long `sessions.json` remembers a session the exporter hasn't seen a record of (see [root_session_id](#root_session_id-whole-request-grouping)). `0` = never forget |
| `index_prefix` | `HERMES_ATP_EXPORT_INDEX_PREFIX` | `hermes-atp` | If you change it, change the roles, template and data view too |
| `batch_size`, `batch_bytes`, `poll_interval`, `backoff_initial`, `backoff_max`, `timeout` | | 500, 5 MB, 2 s, 1 s, 60 s, 30 s | |
| `allow_insecure_http` | `HERMES_ES_ALLOW_INSECURE_HTTP` | `false` | See "Plain HTTP" below |

The exporter never prints or logs a password, an API key or an `Authorization` header.
`--check-config` shows them as `(set)`.

### Running on nuc-hermes (push mode, systemd)

1. Copy `implementations/hermes-plugin/` to `/opt/hermes-atp/hermes-plugin/`.
2. Copy `certs/ca/ca.crt` from us-solebay to `/etc/hermes-atp/es-ca.crt`. It's a public
   certificate: copy it by any means, but check its fingerprint, for example
   `openssl x509 -noout -fingerprint -sha256 -in …` on both hosts.
3. Put the `hermes_exporter` password in `/etc/hermes-atp/es-password`, mode 0640,
   root:hermes. Create the file empty first, then write the password with an editor, never on
   a command line.
4. Install `examples/export.push.json` as `/etc/hermes-atp/export.json` and fill in
   `<SOLEBAY_IP>` and the Hermes user's paths.
5. Install `examples/hermes-atp-export.service` and enable it:
   `systemctl enable --now hermes-atp-export`, then follow it with
   `journalctl -u hermes-atp-export -f`.

The unit runs as the Hermes user, with the home directory read-only and a private state
directory (`/var/lib/hermes-atp-export`). Memory and CPU are capped, and it runs at idle I/O
priority so it can never slow Hermes down. To try it by hand first:
`python3 /opt/hermes-atp/hermes-plugin/elastic/exporter/hermes_atp_export.py --config /etc/hermes-atp/export.json --check-config`.

**API key instead of a password (optional).** On us-solebay, as `elastic`, create a key that
is limited to the same write-only privileges:

```sh
curl --cacert certs/ca/ca.crt -u elastic -X POST https://<SOLEBAY_IP>:9200/_security/api_key \
  -H 'Content-Type: application/json' -d '{"name":"hermes-exporter-nuc","expiration":"365d",
  "role_descriptors":{"hermes_exporter":{"cluster":[],"indices":[{"names":["hermes-atp-records-*"],
  "privileges":["create_doc","auto_configure"]}]}}}'
```

Put the `encoded` value from the response into a 0600 file and set `api_key_file`. To revoke
it, run `DELETE /_security/api_key` with `{"name":"hermes-exporter-nuc"}`.

**Plain HTTP.** `http://` URLs are refused unless `allow_insecure_http` is set. Don't set it
for nuc-hermes → us-solebay. Without TLS:
* the `hermes_exporter` password or API key crosses the VLAN boundary in clear text, on every
  request;
* anyone on the path can read every record (models, tool names, session structure and, if
  shipped, bodies);
* anyone on the path can inject documents or suppress them.

Signatures still let `verify` detect forged records, but they don't protect confidentiality
or the credentials. Plain HTTP is only acceptable against a test cluster on localhost.

### What the exporter can and can't do to Elasticsearch

`hermes_exporter` (or its API key) has the index privileges `create_doc` and `auto_configure`
on `hermes-atp-records-*` and nothing else. It can't read, search, update, overwrite or delete
documents, can't touch other indices, templates or the cluster, and can't mint API keys.
These were all checked on a real 9.5.6 cluster (see Tests).

So a compromised NUC can append junk to these indices, but it can't erase or alter what's
already been shipped. Anything forged shows up as a verify failure, and a forged copy can't
replace a genuine record, because of the `_id` rule above.

## Copy mode (fallback)

Use copy mode if you'd rather not let nuc-hermes reach Elasticsearch at all. The same
exporter runs on us-solebay against copies of the log, with `--once` from a systemd timer. It
stays idempotent when the file is re-copied whole, has lines appended, or is replaced or
truncated, because `_id` is the record hash and the checkpoint is keyed by a hash of the
whole already-shipped prefix (tested both against the fake ES and against real
Elasticsearch).

* **Copying:** the copy should be **started from the NUC**, so the "no inbound to the NUC"
  rule still holds. In OPNsense that's a TCP 22 pass rule to us-solebay instead of the
  TCP 9200 one. Then:
  * On us-solebay, give a dedicated user an `authorized_keys` entry restricted to one
    directory, for example
    `command="rrsync -wo /srv/hermes-atp/incoming",restrict ssh-ed25519 AAAA… hermes-atp-copy`.
  * On the NUC, a timer runs
    `rsync -t ~/.hermes/atp/records.jsonl hermes-atp-copy@<SOLEBAY_IP>:`.
* **Key:** copy `key.pub` to us-solebay **once, out of band**, and don't let the copy job
  overwrite it. Verification is only meaningful if the key comes from somewhere the audited
  host can't change.
* **Exporter:** install `examples/export.copy.json` (it points at `https://localhost:9200`)
  plus `examples/hermes-atp-export-copy.service` and `.timer`.

Copy mode adds latency (the timer interval). Records only ship once a copy contains their
complete line.

## Dashboard

`setup` imports `kibana/hermes-atp-dashboard.ndjson` and `kibana/hermes-atp-lifecycle.ndjson`
automatically. To import one by hand (each file carries the shared data view, so either imports
on its own):
* **Kibana UI:** Stack Management → Saved objects → Import, with "overwrite" on.
* **curl:** `curl --cacert certs/ca/ca.crt -u elastic -H 'kbn-xsrf: true' -F file=@kibana/hermes-atp-dashboard.ndjson 'https://localhost:5601/api/saved_objects/_import?overwrite=true'`.

To open it, run `ssh -L 5601:localhost:5601 us-solebay` (Kibana listens on us-solebay's
localhost only), browse to `https://localhost:5601`, log in as `hermes_viewer`, and go to
Dashboards → **Hermes ATP overview**. Your browser will warn about the self-signed CA unless
you trust `certs/ca/ca.crt`.

| Panel | Shows |
|---|---|
| Sessions over time | Unique `session_id` per interval (subagent sessions count as sessions) |
| Anomalies (verify failures) | Count of anomaly records (`anomaly: true`): everything that failed an ingest check and was stored under an `anomaly-*` `_id` |
| Model calls by model | `post_api_request` count over time, split by `model` |
| Model call latency (ms) | Median and p95 `api_duration_ms` of `post_api_request` |
| Tool calls by name | `post_tool_call` count by `tool_name` |
| Subagent links | Table of parent session → child session (each child's first record carries `parent_session_id`) |
| Anomaly records by kind, reason, session and line | One row per anomaly: `verify.errors.kind` (tampered, missing, out-of-order, body-mismatch), `verify.errors.reason`, `session_id`, log file and line |

### Request lifecycle dashboard

Dashboards → **Hermes ATP request lifecycle** follows one request end to end: the parent Hermes
session plus the subagent sessions it delegated to (`delegate_task`). Everything on it is free
Basic-license Kibana (Lens, Vega/Vega-Lite, controls, Discover). It opens on the last 24 hours.

* **Controls** (top row): **Root session (whole request)**, **Session**, **Turn** and
  **Event** options lists. They filter every panel, Vega included. Pick a top-level session in
  **Root session** to see the whole request: the parent plus all of its subagents, nested ones
  included (it filters on `root_session_id`, see
  [root_session_id](#root_session_id-whole-request-grouping)). **Session** then narrows to
  single sessions within it. Records exported before `root_session_id` existed only show up
  under **Root session** after the backfill.
* **Tiles:** tokens (`tokens.total`), elapsed (first → last record), model time
  (`api_duration_ms`), tool time (`duration_ms`), failed steps (`api_request_error`,
  `post_tool_call` whose `status` isn't `ok`, or any record with an `error_type`; the tree's
  red ring and the waterfall's red marker use the same test), retries (`pre_api_request` with
  `retry_count > 0`) and the ingest-verify pass rate (`verify.valid`).
* **Session labels** (tree and waterfall): role plus the last 6 characters of the session id,
  e.g. `parent · …demo-1`, `sub · …d7e34b`, `sub² · …aa11bb` (a subagent's subagent), up to
  `sub⁴⁺`. The role comes from the subagent links in the time range, not from the dashboard
  filters, so a session keeps its label when you filter down to it. Hover for the full id.
  Labels are distinct within a view: if two sessions would get the same label, both show the
  last 12 characters instead, and if those match too, ` [1]`, ` [2]`, … in order of session
  start (then id).
* **Session tree** (Vega): one node per session, parent on the left, subagents to the right
  (a grandchild goes one level further). The link comes from the child session's **first
  record** (`seq` 0), which carries `parent_session_id` plus `parent_turn_id` /
  `parent_subagent_id` (hover a node for them). Node size is tokens, colour is model + tool
  ms, a red ring means the session has a failed step. A dashed outline means the session
  names a parent that isn't in the current selection, so it's drawn at the top level.
* **Step waterfall** (Vega-Lite): one bar per completed step (model call, tool call, API
  error). The bar ends at the completion record's `@timestamp` and is `duration_ms` /
  `api_duration_ms` long. Rows are sessions in start order, then `seq`. An orange diamond is a
  step that started (`pre_*`) but has no completion record (still running, or the host
  crashed). A failed step has a red outline and a red ring at its end (legend: *failed step*),
  like the tree's red ring. A range with no records shows "No steps in this range". Hover for
  tool/model, status, tokens and verify status.
* **Steps** (saved Discover session): one row per record, sorted `session_id` then `seq`, with
  `seq`, `event`, `tool_name`, `model`, `status`, `duration_ms`, `api_duration_ms`,
  `tokens.total` and `verify.status`, so each session reads top to bottom like a transcript.
  Open it in Discover to add columns.

Limits of what the records can show:
* Recorder timestamps are whole UTC seconds, so waterfall bars are placed to the second;
  `seq` (and the log line) gives the exact order within a session.
* **Caps:** the tree shows up to **500 sessions** (earliest first) and the waterfall reads up
  to **2,000 records** (oldest first) per view. When a cap is hit the panel says so in orange
  at its top right, e.g. "showing first 500 sessions — narrow the range or pick a session" or
  "showing first 2,000 of 7,345 records — …" (the tree asks Elasticsearch for 501 sessions; the
  waterfall compares `hits.total`, exact up to 10,000, shown as "10,000+" beyond). Everything
  past the cap is simply not drawn; the tiles and the Steps table are not capped. Over a long
  time range bars also get very thin: pick a session or zoom the time range.
* Hiding a child's first record (for example with an **Event** filter that excludes
  `pre_api_request`) drops its parent link, so the child shows at the top level.

## Network

nuc-hermes sits on its own VLAN behind an **OPNsense** firewall. Exactly one flow is needed
in push mode: **nuc-hermes → us-solebay, TCP 9200, HTTPS.** It's one-way: the NUC opens the
connection, and only reply traffic for that connection comes back, via the firewall state
table. Nothing is allowed inbound to the NUC. Kibana (5601) isn't reachable from the Hermes
VLAN at all. The addresses below are placeholders: `<NUC_IP>` is nuc-hermes, `<SOLEBAY_IP>`
is us-solebay.

### OPNsense rule (least privilege)

1. **Firewall → Aliases:** create three aliases.
   * `nuc_hermes`: type Host(s), content `<NUC_IP>`.
   * `us_solebay`: type Host(s), content `<SOLEBAY_IP>`.
   * `es_https`: type Port(s), content `9200`.
2. **Firewall → Rules → *[the Hermes VLAN interface]***: add one rule.

   | Field | Value |
   |---|---|
   | Action | Pass |
   | Quick | ✓ (first match wins) |
   | Interface | the Hermes VLAN interface (the rule applies to traffic entering it from the NUC) |
   | Direction | in |
   | TCP/IP version | IPv4 (add an IPv6 twin only if you use IPv6 there) |
   | Protocol | TCP |
   | Source | `nuc_hermes` (single host, not "Hermes net") |
   | Source port | any |
   | Destination | `us_solebay` (single host) |
   | Destination port | `es_https` (9200 only) |
   | State type | keep state (the default): stateful, so replies are allowed only for connections the NUC opened |
   | Log | ✓ recommended |
   | Description | `Hermes ATP export: nuc-hermes -> us-solebay ES 9200 (one-way)` |

3. **Placement:** put the rule **above** any block rule on that interface and above the
   interface's default deny. Rules are evaluated top-down and the first quick match wins.
   Don't add any other pass rules for the NUC as part of this work:
   * no rule for 5601 (Kibana) or 9300 (transport);
   * no "Hermes net → any" rule;
   * nothing on the us-solebay or LAN side that passes *new* connections to `<NUC_IP>`. None
     is needed, because reply traffic rides on the state entry. If that network has a broad
     "LAN → any" rule, add a block rule for "LAN net → Hermes VLAN net" above it.
4. Use the IP in `es_url` (it's in the certificate via `ES_PUBLIC_IP`), so the NUC doesn't
   also need a DNS rule.
5. **Test it from nuc-hermes:**
   * `curl --cacert /etc/hermes-atp/es-ca.crt https://<SOLEBAY_IP>:9200` should return a 401
     JSON body. That means reachable, TLS OK, and anonymous access refused.
   * `nc -vz -w3 <SOLEBAY_IP> 5601` and `nc -vz -w3 <SOLEBAY_IP> 22` should time out.
   * From us-solebay, `nc -vz -w3 <NUC_IP> 22` should time out.

### us-solebay host firewall (defence in depth)

Bind Elasticsearch to the LAN address only (`ES_BIND_ADDR=<SOLEBAY_IP>`) and Kibana to
localhost (`KIBANA_BIND_ADDR=127.0.0.1`, the default). Then allow 9200 only from `<NUC_IP>`.

**Important:** ports published by Docker bypass ufw and the `INPUT` chain, because Docker
DNATs them in its own chains. With the stack running in Docker, the rule that actually works
goes in the **`DOCKER-USER`** chain. `<LAN_IF>` is us-solebay's LAN interface, for example
`eth0`. Scoping by interface keeps the Kibana → Elasticsearch traffic inside Docker
unaffected.

```sh
# iptables (run as root; -I inserts at the top, so add the DROP first, then the ACCEPT above it)
iptables -I DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 9200 --ctdir ORIGINAL -j DROP
iptables -I DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 9200 --ctdir ORIGINAL -s <NUC_IP> -j ACCEPT
iptables -I DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 5601 --ctdir ORIGINAL -j DROP
# persist with your distro's mechanism (e.g. iptables-persistent: netfilter-persistent save)
```

With **ufw**, keep its normal policy and put the same rules in `/etc/ufw/after.rules`, after
the final `COMMIT` of the `*filter` table, so they survive reloads:

```
*filter
:DOCKER-USER - [0:0]
-A DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 9200 --ctdir ORIGINAL -s <NUC_IP> -j RETURN
-A DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 9200 --ctdir ORIGINAL -j DROP
-A DOCKER-USER -i <LAN_IF> -p tcp -m conntrack --ctorigdstport 5601 --ctdir ORIGINAL -j DROP
COMMIT
```

Then run `ufw reload`. The usual ufw rule is still worth having for documentation, and it's
the one that matters if Elasticsearch ever runs outside Docker:

```sh
ufw default deny incoming
ufw allow from <NUC_IP> to <SOLEBAY_IP> port 9200 proto tcp comment 'Hermes ATP exporter'
```

The equivalent without Docker in the path:
`iptables -A INPUT -p tcp --dport 9200 -s <NUC_IP> -m conntrack --ctstate NEW -j ACCEPT`,
followed by `iptables -A INPUT -p tcp --dport 9200 -j DROP`.

These host rules are written to the documented Docker and ufw behaviour but haven't been run
on us-solebay. David reviews and applies them himself (see "Who applies these rules"), then checks that `nc -vz <SOLEBAY_IP> 9200` works from the NUC and
fails from any other host.

## Backlog (priority order)

1. **Index retention: NEXT.** us-solebay is a shared host, so the indices must not grow
   without bound. Add an ILM policy (available on Basic) with a delete phase on
   `hermes-atp-records-*`, or a simple scheduled delete of monthly indices older than an
   agreed age. Until then, indices are monthly and deleted by hand.
2. **Scheduled verify.** A job on us-solebay that runs `atp_cli.py verify` over the shipped
   logs and records the authoritative verdict next to the provisional ingest result.
3. **Snapshots.** A snapshot repository and schedule (available on Basic) so losing `esdata`
   doesn't lose the index.
4. **Rotated files in copy mode.** Carry session chain state across separately copied
   rotated files, so a session split across two files doesn't show a spurious chain error.

## Limitations

* **Ingest verify is provisional**, as described above. It has no look-ahead and no
  whole-log warnings. Tail truncation is undetectable from the log alone, as with `verify`.
  Backlog item 2 closes this.
* **In-place rewrites:** in push mode, a same-length rewrite of the *open* file is only
  noticed when the exporter reopens it (restart or rotation). Copy mode re-hashes on every
  run.
* **Single node with 0 replicas:** no redundancy. Losing `esdata` loses the index, but the
  log on nuc-hermes stays the source of truth and can be re-shipped.
* **The exporter's chain state is per file** (backlog item 4).
